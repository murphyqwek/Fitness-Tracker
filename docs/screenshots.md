# Скриншоты для README

В README подключены снимки интерфейса (`docs/img/dashboard.png`, `docs/img/exercises.png`), дашборда метрик (`docs/img/grafana-metrics.png`) и логов (`docs/img/grafana-logs.png`). Ниже — сценарий получения демонстрационных данных и обновления снимков Grafana.

## Какие кадры подготовить

| Файл в `docs/img/` | Что показать | Зачем |
| --- | --- | --- |
| `grafana-metrics.png` | Дашборд Fitness API: доступность, запросы/с, p95 поиска, новые тренировки, результаты входа, очередь Outbox | Основная иллюстрация раздела метрик |
| `grafana-logs.png` | Explore с Loki: записи API и consumer, JSON-поля события | Показать путь тренировки через логи двух сервисов |

Лучше начать с двух кадров Grafana. Рекомендуемый размер — около 1600×900 или 1920×1080, формат PNG, единая тема интерфейса. На кадре должны читаться названия панелей, единицы измерения, легенды и выбранный период.

## 1. Подключить источники

1. Запустить сервер мониторинга по [инструкции](../Docker/monitoring/README.md) и Alloy по [инструкции](../Docker/alloy/README.md).
2. Открыть Grafana через SSH-туннель. Выбрать Prometheus в Explore и выполнить `up{job="fitness-api"}`. Должно быть `1`.
3. В Explore выбрать Loki и выполнить `{service_name=~"fitness-api|fitness-analytics"} | json`.

Текущие конфиги рассчитаны на два сервера с WireGuard: API — `10.50.0.1`, сервер мониторинга — `10.50.0.2`. Локальный `docker-compose.local.yml` запускает только приложение и открывает его метрики на localhost. Он не подключает Prometheus автоматически; для локального варианта потребуется отдельно настроить сеть и target, доступный из контейнера Prometheus.

## 2. Собрать дашборд Fitness API

Готовый дашборд находится в [`fitness-api.json`](../Docker/monitoring/grafana/dashboards/fitness-api.json). Подключите его через [обновление серверного Compose или ручной импорт](../Docker/monitoring/README.md#дашборд-fitness-api), затем откройте **Fitness Tracker → Fitness API**. Вручную создавать панели не требуется.

В дашборде настроены следующие панели с источником Prometheus:

| Панель | Вид | Запрос / настройки |
| --- | --- | --- |
| Доступность API | Stat | `up{job="fitness-api"}`; соответствия `1 → UP`, `0 → DOWN` |
| Запросы в секунду | Time series | `sum(rate(http_requests_received_total{job="fitness-api"}[5m]))`; единица — запросов/с |
| p95 поиска упражнений | Time series | Запрос ниже; единица — секунды; легенда `{{operation}}` |
| Новые тренировки за час | Stat | `sum(increase(fitness_workouts_created_total{job="fitness-api"}[1h]))` |
| Проверки логина за час | Bar gauge | `sum by (result) (increase(fitness_login_attempts_total{job="fitness-api"}[1h]))`; легенда `{{result}}` |
| Ожидающие сообщения Outbox | Time series | `fitness_outbox_pending_messages{job="fitness-api"}`; минимум — `0` |

Запрос для p95:

```promql
histogram_quantile(0.95,
  sum by (le, operation) (
    rate(fitness_exercise_retrieval_duration_seconds_bucket{job="fitness-api"}[5m])
  )
)
```

Выберите период «последние 15–30 минут» и обновление раз в 15 секунд. Дашборд уже сохранён в JSON и загружается автоматически. При подключении через provisioning правки вносите в исходный JSON; для экспериментов сохраните отдельную копию в Grafana. Ноль не подставляется вместо отсутствующих метрик.

## 3. Получить данные

Используйте тестовый аккаунт и среду, на которой допустимы демонстрационные записи:

1. Дождитесь как минимум двух успешных опросов Prometheus **до** действий, чтобы у счётчиков появилась начальная точка.
2. Зарегистрируйте пользователя, выполните успешный вход и одну попытку с неверным паролем.
3. Несколько минут выполняйте поиск упражнений с разными фильтрами и открывайте карточки. Запросы должны попадать на тот API, который опрашивает Prometheus.
4. Сохраните 2–3 новые тренировки и дождитесь появления аналитики. Для создания через API каждому новому запросу нужен собственный UUID в `Idempotency-Key`.
5. Дайте Prometheus собрать ещё несколько точек. При небольшом числе запросов p95 может быть нестабильным; подпись снимка должна отражать демонстрационную нагрузку.

Для равномерного потока запросов можно в отдельной Bash-сессии выполнить небольшой цикл на своей локальной или тестовой среде:

```bash
for i in {1..120}; do
  curl --fail --silent --output /dev/null 'http://localhost:8080/api/v1/exercise?page=1&size=10' || break
  sleep 2
done
```

Нулевая очередь Outbox при исправной доставке — ожидаемый результат. Не нужно останавливать Kafka на рабочем сервере ради графика. `increase` может возвращать дробное значение из-за экстраполяции, а не из-за создания «части тренировки».

Сохраните дашборд как `docs/img/grafana-metrics.png`.

## 4. Снять логи обработки тренировки

В Explore → Loki выберите время создания тестовой тренировки и запрос:

```logql
{service_name=~"fitness-api|fitness-analytics"} | json
```

Найдите сообщение API о сохранении тренировки и Outbox-события, затем сообщение consumer о завершении обработки и commit offset. Для поиска конкретного события скопируйте его `EventId` и подставьте вместо `EVENT_UUID`:

```logql
{service_name=~"fitness-api|fitness-analytics"} |= "EVENT_UUID" | json
```

Разверните JSON-поля так, чтобы читались `Service`, `EventId`, `WorkoutId` и, у consumer, `Topic`, `Partition`, `Offset`. Это сопоставление логов по событию; распределённая трассировка в проекте отдельно не настроена.

Перед снимком скройте персональные данные, cookies, токены, пароли и адреса серверов, если они видны. Сохраните кадр как `docs/img/grafana-logs.png`.
